Executive summary

Not ready for go-live today. Ready within the window if we start with the platform.

  • Too much power in the wrong places. A build pipeline account holds the cluster's master key, and some apps control the servers they run on.
  • Nothing checks what goes in. No gate stops a dangerous configuration, and no check that what runs is what we built.
  • Nothing separates apps from each other. Every app can reach every other app; passwords sit where many can read them.
  • We wouldn't know. Audit logging is off and there's no runtime detection.

The design as one story

Prevent what we can, contain what gets through, detect the rest

1 · Prevent

Pipeline gates + admission control. Signed images only. CI holds no cluster credentials: the cluster pulls approved changes from Git.

→

2 · Contain

Default-deny network. One cloud identity per workload. Secrets fetched at runtime, never in Git or images.

→

3 · Detect & respond

Audit log + runtime detection to a write-once archive. Contain without destroying evidence.

Zero-trust networking and identity

Deny by default, allow by request. No service mesh yet, on purpose.

  • Turn on enforcement in the existing VPC CNI; standard NetworkPolicy only, so it ports to AKS and GKE as-is.
  • Default-deny in and out per namespace, rolled out from two weeks of flow logs.
  • No internet by default. Allowed domains go through an egress firewall.
  • Metadata service unreachable from pods (IMDSv2, hop limit 1).
  • One cloud identity per workload (Pod Identity); the node role holds almost nothing.

Service mesh: not for go-live

For: mTLS everywhere, L7 authorisation, uniform across clouds.

Against, now: it lands on a stretched team; sidecars are a risk for the COTS image; none of the Critical findings is fixed by a mesh.

Revisit in 2 quarters if: the standard requires in-cluster mTLS, service-to-service calls outgrow IP rules, or AKS/GKE need one story. Then Istio ambient (no sidecars).

Runtime detection and incident response

When prevention fails: see it, contain it, keep the evidence

Detection

  • Falco on every node: same rules on EKS, AKS, GKE.
  • Audit log rules: new cluster-admin binding, secret listing.
  • GuardDuty as a second opinion on AWS.
  • Only Critical pages; two-week baseline before anything pages; every paging rule has a runbook.

Scenario: confirmed container escape attempt

1Capture first (memory checkpoint, filesystem diff, logs), from outside the container
2Relabel the pod: it leaves the Service, a clean replica starts, a pre-staged policy isolates it
3Cordon, don't drain the node; swap it to a forensic security group
4Revoke and rotate every credential the pod and node could reach
5Replace, don't clean: rebuild from Git at signed digests
ITSO during the incident: fixed-cadence updates with "decisions needed from you". Afterwards: root cause, impact evidence, dated actions.

Decision 1 · COTS product

Go live with the vendor image at Medium residual risk, for 6 months

Assumed gap: end-of-life base OS with unfixable CVEs, runs as root, needs a writable filesystem. Vendor won't rebuild without a paid contract.

Compensating controls (reused, not invented)

  • Narrow admission exception: only this exact digest, still no privileged or host access
  • Dedicated nodes, 3-flow network allowlist, one licence domain
  • Strict runtime baseline; auto-quarantine on drop-and-execute
  • Own secrets store and DB user; daily KEV check reopens the decision
Rating
InherentHigh
Residual, with controlsMedium
Not covered: an RCE in the product itself would still expose its own data. The controls limit where an attacker goes next and make sure we see it.
Ask: system owner accepts, ITSO endorses. 6 months, quarterly review, funded exit: support contract, SaaS, our own rebuild, or replace.

The first 90 days

Blockers first, platform next, then prove it works

Weeks 1–2 · Blockers

  • Confirm these findings against the real estate, with the delivery teams
  • Remove the cluster-admin binding; scope CI to its namespaces
  • Remove privileged and host-access pods; rotate exposed secrets
  • Turn on audit logging; Pod Security in warn mode everywhere

Weeks 3–6 · Platform, then go-live

  • Policy gates and admission: audit → enforce
  • Default-deny networking, namespace by namespace
  • Pod Identity, IMDSv2; secrets into Secrets Manager
  • Image signing; COTS controls and signed acceptance

Weeks 7–12 · Prove and harden

  • GitOps cut-over: CI loses cluster access entirely
  • Falco paging on; soft gates ratchet to hard
  • First cluster rebuild drill and DB restore test
  • Run the same policies against a test AKS/GKE cluster
How I'd measure it: blockers closed with evidence, % of namespaces at default-deny and Pod Security restricted, time to detect a test binding, and measured rebuild time against the 2-hour target.
